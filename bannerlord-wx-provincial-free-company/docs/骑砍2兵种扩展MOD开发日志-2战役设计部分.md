## 从混合记录迁入的战役结论

### 原记录009：长期玩法与纯XML边界

- 同一个公共T2提供四个升级目标时，玩家和NPC都能在任意地点选择任意地域路线；纯XML不会保存兵种出生地。
- 真正的地域招募必须建立独立地域根兵种，并研究聚落志愿兵模板、地域判断和C#行为。
- 长期构想包括地域招募、战俘转化、酒馆自由军和海战扩展；其中地域招募是当前优先目标。
- NPC自动升级会产生不可预测的混编比例，因此必须观察世界军队生态，而不能只测玩家部队。

### 原记录013：招募费与维护费

- `NPCCharacters.xsd` 没有可直接设置的 `wage`、`recruitment_cost` 或 `salary` 字段。
- 默认维护费由 `DefaultPartyWageModel` 按兵阶、职业和相关修正计算。
- 默认招募费按等级、骑兵马匹成本、职业和英雄技能/Perk计算。
- 当前地域 T1/T2 保持 `occupation="Soldier"`，暂不通过修改等级或职业间接操纵费用。
- 若未来确需兵种ID特判费用，应单独包装工资/招募费用模型，并评估版本兼容和其他MOD冲突；不与第一版地域征兵同时引入。

### 原记录022、023：战役数据层前置成果

- 四套独立地域T1/T2已经建立，每条路线只能单线进入对应T3，兵种树本身能够保存地域身份。
- v0.4.2 已删除旧共同 T2 和帝国新兵公共入口，不保留旧共同 T2 存档兼容；四条地域树暂时没有正常战役招募渠道。
- v0.4.2 仍未修改志愿兵模型、AI、费用或其他持续运行的战役逻辑。
- v0.4.3 曾为北境 T1–T5 增加全线水兵身份；v0.4.4 已将其收紧为仅 T4/T5 拥有 `NavalSoldier` 与 80/90 的 `Mariner`。
- 地域兵仍未接入志愿兵池，因此 v0.4.4 目前不会在正常新战役中自然改变 NPC 军队构成。
- 当前模块仍为XML/XSLT；引入战役层后将首次增加C# DLL，因此必须单独建立编译、加载、诊断和兼容基线。

## 战役记录 001（原全局记录 020）：v0.3.8 对战役生态的全局影响评估

**日期：** 2026-11-05

**目标：** 在进入 v0.4 设计前，不再只按单条兵种线观察强弱，而是评估 v0.3.8 对战役模式、沙盒模式、NPC 军队构成和长期势力生态的影响。

**环境：** Bannerlord `v1.4.8`、War Sails / NavalDLC `v1.2.8`、模块 `WXProvincialFreeCompany v0.3.8`

### 1. 结论摘要

v0.3.8 的单场战斗体验已经基本成立，但它在长期战役中的最大风险并不是某个兵种数值偏高，而是**行省辅助军进入世界的方式过于普遍**：模块把 `行省征召兵` 直接追加到了原版 `帝国新兵` 的公共升级目标中，因此任何持有帝国新兵的玩家、NPC 领主、叛军或其他合格队伍，都可能把原本的帝国新兵升级进 MOD 路线。

这意味着当前版本并不是“增加少量边疆特色部队”，而是为帝国公共新兵追加了第二套覆盖步兵、远程与骑射职能的完整兵种体系。时间越长、升级次数越多，影响越明显。

因此 v0.4 的优先问题应从“继续增加兵种”转为：

> 让行省辅助军以合适的数量、在合适的地区、进入合适的人手中。

### 2. 战役模式与沙盒模式是否不同

- 模块在 `SubModule.xml` 中同时加载于 `Campaign` 与 `CampaignStoryMode`。
- 战役模式和沙盒模式共用招募、兵种升级、NPC 队伍、驻军、工资与自动战斗等核心系统。
- 战役模式额外包含主线任务和剧情角色，但 v0.3.8 没有修改任务、王国外交、剧情触发器或故事专用代码。
- 因而两种模式受到的军事生态影响基本相同；差异主要来自剧情进程，而不是本 MOD 的兵种逻辑。

### 3. v0.3.8 实际改动了什么

1. 在原版 `imperial_recruit` 的升级目标中追加 `wx_provincial_levy`，同时保留原版帝国步兵和帝国射手入口。
2. 从共同 T2 行省征召兵展开北、南、西、东四条 T3–T5 路线，分别提供盾斧步兵、标枪双手突击兵、重弩兵和骑射兵。
3. 通过 XSLT 把原版帝国禁卫射手、帝国军士弩手的战斗头盔稳定替换为金色禁卫射手盔。
4. 没有新增 C# DLL、Harmony 补丁、招募菜单、结算逻辑、独立工资公式或独立 AI 行为。

因此，模块的运行性能负担很低；真正重要的是原版 AI 如何读取被扩大的公共升级树。

### 4. 对玩家的影响

#### 4.1 帝国阵营玩家

- 从最常见的帝国新兵即可进入四条辅助军路线，组建难度很低。
- 帝国兵种体系原有的角色缺口被明显补齐，尤其是平民骑射线和特色突击步兵线。
- 玩家不再需要通过俘虏、异文化村庄或长期跨境招募来补充这些角色，帝国军队的“全能化”程度提高。
- 南境路线当前同阶表现偏强，却与普通同阶兵共用原版费用体系，可能形成高性价比最优解。

#### 4.2 非帝国阵营玩家

- 占领或路过帝国文化定居点时，仍可招募帝国新兵并升级为辅助军，符合“使用帝国边境投效者”的角色扮演目标。
- 但路线目前没有地理限制；在北境招募到的新兵也能选择南境、东境或西境训练，地域叙事只存在于名称和装备中。
- 从俘虏转化、解救部队等渠道得到帝国新兵后，同样可以进入 MOD 路线。

#### 4.3 已有存档

- 启用 MOD 后，存档中既有的帝国新兵会立即读取新增升级目标；不必为了看到路线强制新开存档。
- 已经升级完成的原版兵不会被自动替换，世界军队构成会随之后的招募和升级逐步变化。
- 一旦自定义兵种 ID 已进入玩家、领主、驻军或俘虏名册，不应直接移除 MOD；缺失兵种定义可能造成存档异常。

### 5. 对 NPC 领主与世界军队的影响

#### 5.1 MOD 没有直接替换 NPC 的招募模板

- 原版帝国领主、聚落和叛军模板仍然生成原版帝国新兵、步兵和射手。
- MOD 不会在招募瞬间把领主整支军队替换成行省辅助军。
- 变化发生在这些帝国新兵获得经验并触发自动升级之后。

#### 5.2 “兵种偏好”准确说是升级阵型偏好

本地 v1.4.8 程序集显示，`PartyUpgraderCampaignBehavior` 会枚举当前兵种的全部合法升级目标，再让 `DefaultPartyTroopUpgradeModel.GetUpgradeChanceForTroopUpgrade` 为各目标赋权。它考虑经验、金币、工资上限、升级所需物品和队伍条件，随后按权重选择升级目标。

- 普通候选目标基础权重为 `1`。
- 如果队伍领主设置了 `PreferredUpgradeFormation`，且某个候选目标的后续兵种树包含该阵型，则该候选目标权重提高到 `9999`。
- 如果领主没有阵型偏好，算法不会每次平均随机，而会根据领主随机值、当前兵种 ID 和兵种等级，为其中一个目标形成近似固定的 `9999` 权重。
- 因此同一个领主在同一个存档中可能长期偏向某条路线，形成看似稳定的军队风格；它不等同于按四条路线平均分配。

对当前帝国新兵的三个一级升级目标而言：

- 步兵偏好可同时命中原版帝国步兵树和包含北/南步兵的 MOD 树。
- 远程偏好可同时命中原版帝国射手树和包含西境弩兵的 MOD 树。
- 骑射偏好只有 MOD 树能够满足，因此可能极强地导向行省征召兵。
- 骑兵偏好在这三个平民升级子树中没有对应终点，候选目标保持普通权重。
- 无显式偏好时，由领主与兵种节点共同计算出的确定性目标会占据绝对权重。

#### 5.3 三大帝国初始领主没有预设阵型偏好

对本机 `Modules\SandBox\ModuleData\heroes.xml` 的完整检查显示：北部帝国、西部帝国和南部帝国的初始命名领主均未填写 `preferred_upgrade_formation`。整个原版 `heroes.xml` 中只有库赛特的蒙楚格显式写入 `HorseArcher`。

没有该 XML 属性时，初始领主的值为“无指定阵型”，其升级路线主要由前述确定性散列分支决定。动态新建的英雄则由 `DefaultHeroCreationModel` 随机生成：四种主阵型各约 10%，其余约 60% 为无指定阵型。该随机逻辑不读取性格、荣誉、仁慈、勇猛、技能或文化。

#### 5.4 长期军队构成

- 不会出现“所有帝国领主立刻全部改用 MOD 兵”的瞬时替换。
- 但部分领主可能在多个升级周期中稳定选择 MOD 入口，并在 T2 再稳定选择某个地域分支。
- 骑射偏好的动态领主尤其可能把 MOD 树当作帝国新兵唯一可达的骑射出口。
- 随着旧兵伤亡和新兵反复补充，某些领主军中辅助军占比可能显著高于预期；另一些领主则可能继续大量使用原版路线。

### 6. 对不同世界系统的影响

#### 6.1 驻军与民兵

- MOD 没有改写民兵兵种节点，因此城镇与村庄的基础民兵不会直接变成辅助军。
- 领主或玩家把 MOD 兵放入驻军后，它们会长期存在；驻军内已有的低阶 MOD 兵也可能继续受原版训练机制影响。
- 这会让辅助军随领地易手进入非帝国势力驻军，但属于人员流动结果，不是文化兵种模板被替换。

#### 6.2 叛军与次级队伍

- 原版帝国叛军模板含有较多帝国新兵，这些新兵同样能读取 MOD 升级入口。
- 商队、民兵、巡逻队或其他队伍是否大量出现 MOD 兵，取决于它们是否实际持有帝国新兵、能否获得经验并执行通用升级行为。

#### 6.3 势力平衡

- 北境提供可靠盾斧步兵，南境提供高杀伤标枪双手突击兵，西境提供持续重弩火力，东境补齐平民骑射。
- 四条路线共同降低了帝国对外族兵种的依赖，使帝国在攻城、野战、反骑、追击和远程消耗方面更完整。
- 南境同阶过强和东境骑射的普及，可能使帝国在自动战斗及长期战争中的实际强度上升。
- 如果辅助军比例过高，帝国原版军团步兵、禁卫射手和军士弩手的视觉与战术身份会被稀释。

#### 6.4 War Sails / 海战

- 南境标枪与双手武器在接舷和狭窄甲板上可能表现突出。
- 北境盾兵在抵挡投射物与接舷推进时具有天然价值。
- 西境弩兵适合接舷前齐射，但无盾设计使其在贴身后仍有明确短板。
- 东境骑射兵在海战中无法发挥坐骑与绕射优势，下马后性价比明显下降。
- MOD 没有修改舰船、海军 AI 或水手模板，影响来自兵种被带入海战后的表现。

#### 6.5 原版帝国远程兵金盔替换

- 该 XSLT 作用于全世界的原版帝国禁卫射手与军士弩手，而不只作用于玩家部队。
- 除视觉统一外，更高的头部防护会带来小幅全局数值增益；它不是纯外观改动。

### 7. 兼容性、性能与维护风险

- **性能风险低：** 当前只有 XML/XSLT，没有持续运行的 DLL 或 Harmony 钩子。
- **存档移除风险中等：** 自定义兵进入存档后不可随意停用模块。
- **同类 MOD 兼容风险中高：** 其他 MOD 若也修改 `imperial_recruit` 升级目标或同两种帝国 T5 远程兵装备，结果取决于加载顺序与 XML/XSLT 合并方式。
- **版本升级风险中等：** 游戏更新若重命名原版兵种、装备节点或调整 XML 结构，需要重新验证 XSLT 匹配结果。
- **剧情风险低：** 当前没有接触主线脚本，但战役任务临时生成的帝国军队仍可能通过通用兵种系统间接受影响。

### 8. v0.4 设计约束

v0.4 不宜继续直接扩展战斗数值，而应先解决分布和控制问题：

1. 重新评估是否继续把行省征召兵直接挂在公共 `imperial_recruit` 下。
2. 为北、南、西、东四条路线建立真实的地域招募来源，而不是允许任意地点自由四选一。
3. 设定辅助军在帝国领主军队中的合理占比，确保原版帝国正规军仍为主体。
4. 保留非帝国玩家在帝国边境获得投效者或地方辅助兵的合理渠道。
5. 保留现有全部兵种 ID，优先采用可迁移方案，避免破坏已经包含 v0.3.8 兵种的存档。
6. 通过 50/100/200 日观察点统计多支帝国领主队伍的原版兵与 MOD 兵比例，再判断是否出现系统性替代。

建议的阶段验收标准是：辅助军能够被看见并形成地域特色，但不能让原版帝国步兵、射手和弩手从多数帝国领主军中消失。

## 战役记录 002（原全局记录 021）：v0.4 地域独立兵源与边疆梯度招募方案

**日期：** 2026-11-05

**目标：** 将 v0.3.8 的公共帝国新兵分支，重构为四套具有真实地域来源的行省辅助兵源；同时使用边疆强度控制其在不同聚落中的出现比例。

**阶段性质：** 设计冻结，尚未进入代码实现。

### 1. 对此前方案的关键修正

同一个 `imperial_recruit` 离开聚落并进入队伍后，只保留兵种 ID、人数、伤员与经验等兵种堆栈数据，不记录出生聚落。来自北、南、西、东不同地区的帝国新兵会合并成同一个兵种堆栈。

因此不能同时满足以下两个条件：

1. 四条地域路线都继续由同一个原版帝国新兵升级；
2. 北方招募的新兵只能进入北境路线，南方招募的新兵只能进入南境路线。

纯 XML 无法根据已经丢失的出生地信息锁定升级方向；若按照升级时所在位置判断，又会导致北方新兵被运到南方后突然变成南境人。v0.4 因此放弃“共同原版 T1 记录地域”的设想。

### 2. 修正后的升级树结构

原版帝国新兵恢复为原版公共兵源，不再通向新的行省辅助军：

```text
原版帝国新兵
├─ 原版帝国步兵
└─ 原版帝国射手
```

四条行省路线从 T1 开始使用彼此独立的兵种 ID：

```text
北境行省新兵 T1
└─ 北境行省征召兵 T2
   └─ 北境行省辅兵 T3
      └─ 北境自由军盾斧兵 T4
         └─ 北境自由军盾卫 T5

南境行省新兵 T1
└─ 南境行省征召兵 T2
   └─ 南境行省掷矛兵 T3
      └─ 南境自由军突击兵 T4
         └─ 南境自由军破阵卫 T5

西境行省新兵 T1
└─ 西境行省征召兵 T2
   └─ 西境行省弩手 T3
      └─ 西境自由军重弩手 T4
         └─ 西境自由军破甲弩卫 T5

东境行省新兵 T1
└─ 东境行省征召兵 T2
   └─ 东境行省骑射手 T3
      └─ 东境自由军游骑射手 T4
         └─ 东境自由军游骑卫 T5
```

四种地域 T1/T2 可以共享“边民被帝国征召”的基础身份、低阶装备档次和数值基线，但每条树只有一个升级目标。地域锁定由兵种树结构本身完成，不依赖 AI 判断、当前位置或额外的逐兵来源记录。

### 3. 默认领主模板保持原版

v0.4 暂不修改 `kingdom_hero_party_empire_template`：

- 帝国领主创建或战败重建时仍获得原版混编部队；初始 MOD 兵数量为 0。
- 领主只有实际前往相应边疆地区补兵，才可能得到当地辅助军。
- 避免三个帝国政权的所有领主在重生时无条件获得同一种辅助军。
- 避免每次战败重建都凭空补发高价值地域兵。
- 保留原版帝国正规军作为军队主体的基础保障。

### 4. 地域招募的技术实现

当前纯 XML 模块需要增加一个尽可能小的 C# 战役模块。计划创建继承原版志愿兵模型的地域志愿兵模型；它只在原版准备生成基础志愿兵时进行窄范围替换。

基本流程：

1. 调用原版 `DefaultVolunteerModel.GetBasicVolunteer`，取得原本应该生成的兵种。
2. 判断要人所在聚落是否存在于地域配置中。
3. 读取该聚落的地域、边疆等级、生成概率与辅助兵槽位上限。
4. 统计该要人当前六个志愿兵槽位中已有的地域兵数量。
5. 未达到上限时，按配置概率把本次基础兵替换为对应的地域 T1。
6. 未命中、达到上限或不属于配置范围时，完整保留原版结果。

伪代码：

```csharp
var original = base.GetBasicVolunteer(notable);
var profile = RegionalConfig.Find(notable.CurrentSettlement);

if (profile == null)
    return original;

if (CountRegionalSlots(notable.VolunteerTypes) >= profile.MaxAuxiliarySlots)
    return original;

if (RandomChance(profile.AuxiliaryChance))
    return profile.RegionalRecruit;

return original;
```

玩家与 NPC 领主继续使用同一套原版志愿兵池，不为 AI 创建专用兵源，也不使用 Harmony 修改领主升级算法。

### 5. 地域按固定地理划分

不以当前统治者或三大帝国政权归属判断地域，而是按聚落 ID 建立静态地理配置：

- 靠近斯特吉亚的帝国聚落归北境。
- 靠近阿塞莱的帝国聚落归南境。
- 靠近瓦兰迪亚的帝国聚落归西境。
- 靠近库赛特的帝国聚落归东境。

城镇、城堡与附属村庄均应获得明确地域。聚落被外族或玩家占领后，仍然生产原来的当地辅助兵，表现当地人口、军事传统和向新统治者投效的可能性。

地域限制只约束兵种的首次产生地点，不限制之后的使用地点。俘虏招降、驻军转移、解救与领地易手仍可让地域兵流动到其他地区。

### 6. 使用“边疆强度”而不是统一占比

20% 不作为全帝国统一比例，只作为帝国核心地区的参考。每个聚落同时配置地域归属和边疆等级：

| 边疆等级 | 地域 T1 生成概率 | 每位要人最多地域兵槽位 | 预期表现 |
|---|---:|---:|---|
| 帝国核心 | 20% | 1/6 | 地域兵只是少量地方人口 |
| 内地行省 | 40% | 2/6 | 正规兵为主，辅助兵稳定可见 |
| 边疆地区 | 65% | 3/6 | 正规兵与辅助兵大致并存 |
| 最前线普通村庄 | 80% | 4/6 | 辅助兵成为当地主要普通兵源 |
| 最前线城堡村庄 | 60% | 2/6 | 保留帝国贵族骑兵兵源 |

概率负责制造自然波动，槽位上限负责避免某位要人的六个槽位全部被地域兵占满。最终数值需通过实机与长期战役统计调整，不视为最终平衡值。

### 7. 城堡附属村庄的特殊保护

原版城堡附属村庄是帝国贵族兵线的重要来源。若直接高概率替换其基础兵，会挤压帝国青年、帝国骑手和具装骑兵的补充。

因此计划：

- 普通边疆村庄可以允许 3–4 个地域兵槽位。
- 最前线城堡附属村庄最多只允许 2 个地域兵槽位。
- 其余槽位继续保留原版贵族兵生产。
- 城镇要人的地域兵上限通常低于周边普通村庄，使城市仍然更接近帝国正规兵与佣兵中心。

### 8. 配置与代码分离

地域表不硬编码在 C# 中，计划新增独立配置文件，例如：

```xml
<RegionalRecruitment>
  <Settlement
    id="settlement_id"
    region="North"
    frontier_level="Frontier"
    auxiliary_chance="0.65"
    max_auxiliary_slots="3" />
</RegionalRecruitment>
```

这样后续可以在不修改兵种代码的情况下调整：

- 聚落属于哪个地域；
- 聚落的边疆等级；
- 地域兵生成概率；
- 每位要人的地域兵槽位上限；
- 城镇、普通村庄和城堡村庄的不同规则。

### 9. 旧存档兼容策略

现有共同 T2 `wx_provincial_levy` 不删除：

- 从原版 `imperial_recruit` 的新升级入口中解除关联。
- 保留兵种定义、名称、装备与现有四个 T3 升级目标。
- 旧存档中已经存在的共同 T2 仍能继续升级。
- 现有四条 T3–T5 兵种 ID 全部保留，避免存档丢失角色定义。
- 新产生的兵源改用四套新地域 T1/T2；旧共同 T2 不再进入新的志愿兵池。

## 战役记录 003（原全局记录 024）：统一帝国地理下的地域志愿兵技术方案

**日期：** 2026-11-05
**目标：** 在不破坏帝国贵族兵、原版正规军、NavalDLC 海军线和 AI 原有征兵流程的前提下，让四种地域边民按帝国中心—内地—边疆梯度进入战役志愿兵池
**阶段性质：** 技术路线冻结，尚未进入 C# 代码开发

> 本记录是对记录021技术方案的后续核验与修正。发生冲突时，以本记录为准：改为包装当前有效 `VolunteerModel`，通过“原模型返回值是否恰好为 `imperial_recruit`”保护贵族兵；在没有取得当前志愿兵槽位索引的可靠接口前，不承诺硬编码每位要人的地域兵槽位上限。

### 1. 本机 v1.4.8 API 核验

已只读检查本机 `TaleWorlds.CampaignSystem.dll`，确认当前版本存在以下正式扩展接口：

- `VolunteerModel.GetBasicVolunteer(Hero)`
- `VolunteerModel.GetDailyVolunteerProductionProbability(Hero, int, Settlement)`
- `VolunteerModel.CanHaveRecruits(Hero)`
- `VolunteerModel.MaximumIndexHeroCanRecruitFromHero(...)`
- `VolunteerModel.MaximumIndexGarrisonCanRecruitFromHero(...)`
- `CampaignGameStarter.GetModel<VolunteerModel>()`
- `CampaignGameStarter.AddModel(...)`
- `Hero.HomeSettlement`、`Hero.CurrentSettlement`
- `CultureObject.BasicTroop`、`CultureObject.EliteBasicTroop`

`DefaultVolunteerModel` 不是 sealed，相关方法为 virtual；但为了兼容 NavalDLC 与其他可能先加载的模型，计划不直接假定当前模型必然是原版默认模型，而是包装 `CampaignGameStarter.GetModel<VolunteerModel>()` 返回的当前有效模型。

### 2. 技术实现：志愿兵模型装饰器

地域模型不重新发明原版征兵规则。它先调用当前有效模型，让原版、DLC或前置MOD决定本次应生成什么兵，再只对普通帝国新兵做窄范围替换。

```text
当前有效 VolunteerModel
        │
        ▼
生成原始志愿兵
        │
        ├─ 不是 imperial_recruit
        │      └─ 完整保留
        │
        └─ 是 imperial_recruit
               │
               ▼
        查询要人的 HomeSettlement
               │
               ├─ 无地域配置 → 保留帝国新兵
               └─ 有地域配置
                       │
                       ▼
              按边疆概率生成
              帝国新兵或对应地域 T1
```

建议伪代码：

```csharp
CharacterObject original = innerModel.GetBasicVolunteer(notable);

if (original?.StringId != "imperial_recruit")
    return original;

Settlement home = notable.HomeSettlement ?? notable.CurrentSettlement;

if (!regionalRegistry.TryGetValue(home?.StringId, out RegionalProfile profile))
    return original;

CharacterObject regional = RollRegionalVolunteer(profile);
return regional ?? original;
```

除 `GetBasicVolunteer` 的窄范围替换外，志愿兵生成概率、关系解锁槽位、驻军可用槽位和可招募条件全部委托给当前有效模型。

### 3. 三个帝国政权按统一帝国地理处理

地域判定不读取北部帝国、南部帝国、西部帝国的 faction ID，也不跟随当前统治者变化。每个原帝国城镇和村庄按固定地理配置：

- 靠近斯特吉亚与诺德方向的聚落归北境。
- 靠近阿塞莱方向的聚落归南境。
- 靠近瓦兰迪亚方向的聚落归西境。
- 靠近库赛特方向的聚落归东境。
- 帝国腹地单独标为 Core，可以少量混合四地移民，也可以按最近方向归属。

聚落被外族占领后仍产生当地人口；帝国攻占外国聚落后，也不会立即把当地志愿兵改成帝国行省兵。第一版采用固定地理人口模型，不模拟动态文化同化。

### 4. 中心—内地—边疆梯度

初始建议值：

| 地理层级 | 原版帝国新兵 | 地域边民 T1 | 设计目的 |
|---|---:|---:|---|
| 帝国核心 | 70% | 30% | 正规军占主体，少量地方移民与辅助兵 |
| 内地行省 | 40%–50% | 50%–60% | 正规兵与地方兵稳定并存 |
| 外围边疆 | 15%–25% | 75%–85% | 当地边民成为主要普通兵源 |
| 沿海/海军保护区 | 40%–50% | 50%–60% | 保留帝国步兵与海军升级线来源 |

这些比例是“每次新志愿兵生成时的概率”，不是对单个要人六个槽位的绝对保证。是否额外实现硬性槽位上限，需要在核对 `RecruitmentCampaignBehavior` 的实际写槽顺序后决定，不能仅凭 `GetBasicVolunteer(Hero)` 假设能够获得当前槽位索引。

### 5. 贵族兵种特殊保护

帝国贵族线基础兵 `imperial_vigla_recruit` 与普通 `imperial_recruit` 是不同兵种。装饰器仅在原模型返回值恰好为普通帝国新兵时介入：

```csharp
if (original.StringId != "imperial_recruit")
    return original;
```

因此下列内容原样保留：

- 帝国维格拉新兵及其贵族骑兵升级线。
- 原版根据要人权势、类型和其他条件生成贵族兵的逻辑。
- 佣兵、特殊志愿兵、任务兵与其他文化兵。
- 当前模型或 NavalDLC 返回的任何非 `imperial_recruit` 兵种。
- 志愿兵的生成速度、关系解锁和驻军征募规则。

这比按“城堡村庄统一替换一部分槽位”更可靠：我们先让原版判断是否应当生成贵族兵，只有它明确选择普通帝国新兵后才考虑地域替换。

### 6. 原版正规军与 NavalDLC 海军线保护

地域边民不能完全替代普通帝国新兵，否则会同时减少：

- 帝国步兵、熟练步兵与军团步兵。
- 帝国弓箭手、禁卫射手和军士弩手。
- NavalDLC 从帝国步兵延伸出的帝国随船水手/海军路线。

因此所有地域都保留一定比例的 `imperial_recruit`。沿海城镇、港口附近村庄和海军兵源区采用单独的较低地域替换率，避免海战DLC加入的官方兵种失去稳定入口。

### 7. AI领主、驻军与世界军队

玩家和 AI 共用同一志愿兵池，不建立玩家专属或 AI 专属兵源。

- 帝国领主创建或战败重建时仍使用原版部队模板，不直接凭空获得 MOD 兵。
- 领主访问不同地区征兵时逐渐混入当地行省兵。
- 驻军、俘虏、解救部队和领地易手可以让地域兵跨区流动。
- 部分领主长期在同一战区活动时，会自然形成地域军队风格。
- 需要在 30/60/120 日或 50/100/200 日观察点统计多支帝国部队的原版与 MOD 兵比例。

预期不是让所有帝国领主立即改用行省兵，而是让军队构成逐步反映其长期征兵区域。

### 8. 聚落配置数据

地域表使用独立 XML 配置，由 C# 手动读取，不把大量 settlement ID 硬编码进 DLL：

```xml
<RegionalRecruitment>
  <Settlement
    id="settlement_id"
    region="North"
    frontier_level="Frontier"
    auxiliary_chance="0.80"
    coastal_protection="false" />
</RegionalRecruitment>
```

配置至少需要记录：

- 聚落 `StringId`。
- North、South、West、East 或 Core 地域。
- Core、Inland、Frontier 等边疆等级。
- 地域兵生成概率。
- 是否属于沿海或海军保护区。
- 城镇、普通村庄、城堡附属村庄等类型或备注。
- 必要的单聚落覆盖值。

启动时一次性解析为字典，生成志愿兵时只做 O(1) 查询，避免每日遍历全地图。

### 9. 旧公共入口迁移

当前 XSLT 仍把旧共同 T2 `wx_provincial_levy` 追加为 `imperial_recruit` 的升级目标。如果保留该入口，任何地点的帝国新兵仍可绕过地域系统进入四条路线。

地域志愿兵模型验证通过后应当：

1. 停止向原版帝国新兵追加旧共同 T2 升级目标。
2. 保留 `wx_provincial_levy` 兵种定义和四个 T3 升级目标。
3. 旧存档已经存在的共同 T2 继续有效并可升级。
4. 新产生的四种地域 T1 只能进入各自 T2、T3 路线。
5. 不删除现有 T3–T5 ID，避免旧存档丢失角色定义。

### 10. 已有存档与刷新策略

- 不批量改写存档中当前已经存在的要人志愿兵槽位。
- 旧帝国新兵会被玩家或 AI 招走，空槽随后按新模型自然刷新。

## 战役记录 004（原全局记录 025）：志愿兵槽位自然成长与高阶行省兵来源

**日期：** 2026-11-05
**目标：** 澄清“只在原模型返回普通帝国新兵时介入”是否会导致玩家只能招募地域 T1，并决定是否需要把已经存在的帝国 T2–T4 转换成同阶行省兵
**阶段性质：** 本机 v1.4.8 行为核验与设计修正，尚未进入代码实现

### 1. 结论摘要

“只替换普通帝国新兵”描述的是地域兵种树的出生入口，不是玩家最终只能招募的兵阶。

当前 v1.4.8 会让已经位于要人志愿兵槽中的兵种随时间自动升级。地域 T1 进入槽位后，可以沿自身唯一升级路线自然成长为地域 T2、T3、T4。因此第一版无需扫描并替换已经存在的原版帝国 T2–T4，也能让玩家直接从高权势要人处招募较高阶行省兵。

### 2. 本机 v1.4.8 实际更新流程

已检查本机 `RecruitmentCampaignBehavior.UpdateVolunteersOfNotablesInSettlement` 的当前实现，确认其主要流程为：

1. 对聚落中的每位可提供新兵且仍存活的要人，调用一次当前 `VolunteerModel.GetBasicVolunteer(hero)`，取得本轮空槽所使用的基础兵种。
2. 遍历该要人的 6 个 `VolunteerTypes` 槽位。
3. 空槽在通过 `GetDailyVolunteerProductionProbability` 的生成判定后，写入前述基础兵种。
4. 非空槽若兵种存在升级目标、当前 Tier 低于 `MaxVolunteerTier`，则根据要人 `Power` 与当前兵阶计算每日升级机会。
5. 升级判定命中后，从当前兵种的合法 `UpgradeTargets` 中随机选择一个目标写回该槽位。

本机默认模型核验结果：

```text
DefaultVolunteerModel.MaxVolunteerTier = 4
Hero.MaximumNumberOfVolunteers = 6
```

由于判断条件是“当前 Tier 低于 4 时可以继续升级”，T3 可以在槽位内升级为 T4；T4 达到上限后不再继续升级为 T5。

### 3. 三套兵源的自然成长

#### 原版普通兵源

```text
帝国新兵 T1
├─ 帝国步兵 T2
│  └─ 原版帝国步兵/海军方向继续成长
└─ 帝国弓箭手 T2
   └─ 原版帝国远程方向继续成长
```

#### 原版贵族兵源

```text
帝国维格拉新兵
└─ 帝国贵族骑兵路线继续成长
```

#### 地域行省兵源

```text
北/南/西/东境边民 T1
└─ 对应地域征召兵 T2
   └─ 对应地域辅助兵 T3
      └─ 对应地域自由军 T4
```

四种地域 T1 均只有一个合法升级目标，因此槽位内自动升级不会跨地域串线。玩家访问要人时，既可能看到刚生成的 T1，也可能看到已经等待并成长了一段时间的 T2、T3 或 T4。

### 4. 贵族兵保护覆盖整条路线

地域装饰器仍先取得原模型结果：

```csharp
CharacterObject original = innerModel.GetBasicVolunteer(notable);

if (original?.StringId != "imperial_recruit")
    return original;
```

若原模型返回 `imperial_vigla_recruit`，地域逻辑不会介入。该贵族根兵进入槽位后，由原版自动升级机制继续沿贵族路线成长；后续也不会有每日扫描程序把其 T2、T3、T4 后代转换成地域兵。

保护对象不仅包括贵族兵，还包括佣兵、任务兵、其他文化兵种和任何原模型返回的非普通帝国新兵单位。

### 5. 不采用“同阶事后替换”的原因

将已经存在的原版帝国 T2、T3、T4 转换为同阶地域兵，会带来以下问题：

1. **兵种对应关系含糊。** 北境聚落中的帝国弓箭手若被替换为北境盾斧步兵，会突然改变已经形成的职业训练。
2. **原版正规军被二次侵蚀。** 即使根节点阶段保留了一部分帝国新兵，它们升级后仍可能被地域系统再次转换，最终绕过中心—边疆比例。
3. **已有存档对象被反复改写。** 需要直接扫描和修改 `Hero.VolunteerTypes[index]`，增加读档变化、状态追踪和兼容风险。
4. **需要更深层补丁。** `GetBasicVolunteer` 只负责空槽基础兵；改写既有高阶槽位必须增加每日扫描、额外 CampaignBehavior 或 Harmony 补丁。
5. **不必要。** 原版槽位成长已经能够自然提供地域 T2–T4。

因此地域身份应在兵种进入槽位时确定，之后沿各自兵种树成长，而不是在成长过程中反复改变文化与职业身份。

### 6. 高阶地域兵的两种来源方案

#### 方案 A：完全依赖原版槽位成长（第一版采用）

- 空槽只生成地域 T1 或原版基础兵。
- 地域 T1 根据原版要人权势与每日升级机制自然成长。
- 高权势要人更容易积累 T2–T4，低权势要人以 T1 为主。
- 不改变原版训练时间、槽位成长规律和最高志愿兵 Tier。

这是当前首选方案，因为它只改变兵种树入口，改动范围最小。

#### 方案 B：高权势边疆要人小概率直接生成地域 T2（预留）

技术上，`GetBasicVolunteer` 返回的是 `CharacterObject`，并没有在方法签名上强制必须返回 T1。未来若实测发现地域高阶兵自然成长过慢，可以考虑：

```text
普通边疆要人：以地域 T1 为主
高权势边疆要人：小概率直接生成地域 T2
地域 T3：仅在充分测试后考虑极低概率
地域 T4：不直接生成，只允许槽位自然成长
```

该方案仍然只作用于新空槽，不转换已经存在的原版兵。但它会绕过部分训练时间、提高高阶兵可得性并改变战役强度，因此不进入第一版实现。

### 7. 当前冻结决策

1. 第一版只在原模型返回 `imperial_recruit` 时，按聚落地域概率将新空槽根兵替换为对应地域 T1。
2. 原版普通帝国兵、贵族兵和地域兵进入槽位后，全部交由原版自动升级机制成长。
3. 不扫描、不转换已经存在的原版帝国 T2、T3、T4。
4. 贵族兵从根节点到高阶后代全程不参与地域替换。
5. 志愿兵槽位可自然提供地域 T1–T4；地域 T5仍需招募后在部队中培养。
6. 先通过实机和长期战役统计确认自然成长速度，再决定是否启用“高权势要人小概率直出地域 T2”。

### 8. 后续验收重点

- 记录不同权势要人的地域 T1、T2、T3、T4实际分布。
- 确认地域 T1 在槽位中只沿自身单线升级，不发生跨地域或回到原版路线。
- 确认维格拉新兵及其高阶贵族后代不被替换。
- 对比核心、内地、边疆要人的兵阶和原版/地域兵比例。
- 观察自然成长能否提供足够的地域 T2–T4，而无需直出高阶兵。
- 确认 T4 不会继续在志愿兵槽中升级为 T5。
- 将“是否启用高权势要人直出地域 T2”保留为实测后的平衡开关，而不是预先写死。

## 战役记录 006（原全局记录 029）：v0.4.3 北境水兵身份的战役影响

**日期：** 2026-11-06  
**目标：** 记录北境全线获得 NavalDLC 海军士兵身份后，对未来地域征募与长期战役平衡产生的约束  
**阶段性质：** 兵种数据已经落地，正常战役兵源尚未接入

### 1. 已落地的数据

- 北境 T1–T5 均设置 `NavalSoldier=1`。
- `Mariner` 按 T1–T5 配置为 50、60、70、80、90，与 NavalDLC 诺德兵种的成长方式一致。
- 北境线的陆战装备、战斗技能、兵阶、升级费用计算基础与升级关系不变。
- 本次继续沿用已有 NavalDLC `v1.2.8` 必需依赖，没有增加 C#、Harmony 或新的持续运行模型。

### 2. 当前战役中的实际影响

v0.4.3 仍未把四种地域 T1 接入要人志愿兵槽，因此正常新战役中：

- 玩家和 NPC 不会仅因启用本版本就自然征募出北境水兵。
- 原版帝国领主、驻军和要人兵池不会自动转化为北境线。
- 只有通过自定义战斗、控制台或其他直接生成方式取得北境兵时，其海战身份才会生效。
- 因而本版本暂时不会造成帝国 NPC 舰队突然大量获得水兵，也不会改变三个帝国阵营的常规陆军构成。

### 3. 接入地域征募后的预期影响

未来 `VolunteerModel` 让北境聚落生成北境 T1 后，这条路线会沿原版槽位升级机制自然成长为水兵 T2–T4，玩家招募后可继续培养到 T5。届时需要注意：

1. 北境地域兵在陆战中仍是盾斧重步兵，不应因水兵特性获得额外陆战数值。
2. 海战中他们会免除普通陆军的主要移动、伤害与远程稳定性惩罚，并在海战自动结算中获得更高的兵力价值。
3. 北方沿海和边境要人的地域兵占比将直接影响帝国舰队质量，因此北境生成概率同时也是海军强度参数。
4. 如果北境兵源覆盖过广，三个帝国阵营可能在海战中普遍获得专业接舷兵，削弱诺德海军兵种的独特性。

- 北境地域生成概率主要决定盾斧步兵供给，不再直接等同于帝国海军强度。
- 专业水兵数量由原版升级时间、要人权势、志愿兵槽最高阶和部队成活率自然限制。
- 未来若实测发现 T4 水兵过多或过少，可以调整北境地域概率或升级体验，而不必立即增加新的地理判定层。

v0.5 包装 `CampaignGameStarter` 中当前已经生效的 `VolunteerModel`，不假定它必然是原版 `DefaultVolunteerModel`。除基础兵种选择外，其余方法全部委托给内部模型。

```text

        │
        ▼
original = inner.GetBasicVolunteer(notable)
        │
        ├─ original.StringId != "imperial_recruit"
        │      └─ 原样返回
        │
        └─ original.StringId == "imperial_recruit"
               │
               ▼
        查询要人所属聚落配置
               │
               ├─ 无配置/解析失败 → 返回 original
               └─ 有配置 → 按 0/30/55/80 判定
                                │
                                ├─ 命中 → 对应地域 T1
                                └─ 未命中 → original
```

建议核心代码边界：

```csharp
CharacterObject original = innerModel.GetBasicVolunteer(notable);

if (original?.StringId != "imperial_recruit")
    return original;

Settlement settlement = notable.HomeSettlement ?? notable.CurrentSettlement;

if (!regionalRegistry.TryGetValue(settlement?.StringId, out RegionalProfile profile))
    return original;

return Roll(profile.AuxiliaryChance)
    ? profile.RegionalRecruit
    : original;
```

本机 v1.4.8 `DefaultVolunteerModel.GetBasicVolunteer` 的原版分支为：

### 6. 随机判定与槽位聚集现象

本机 v1.4.8 的 `RecruitmentCampaignBehavior` 会对一名要人先调用一次 `GetBasicVolunteer`，再遍历其六个志愿兵槽位。若同一次更新中有多个空槽通过生成概率，它们可能共享本轮取得的同一种基础兵。

因此：

- 30%/55%/80% 是跨多次更新和大量要人的长期概率。
- 不是每名要人六个槽位的固定组成比例。
- 单个要人短期出现全地域兵或全帝国新兵不自动构成缺陷。
- 概率正确性必须用独立模拟或事件累计统计判断，不能只截图观察一个要人。
- 第一版不为实现硬配额而补丁写槽顺序，也不每日扫描并重写志愿兵槽。

- `.csproj` 不提交任何用户机器的绝对游戏路径；通过 `BannerlordGameDir` 或本地未跟踪 props 传入。
- TaleWorlds 和 NavalDLC 引用设置为不复制，不将官方 DLL 收入 MOD 或 Git。
- `SubModule.xml` 只注册本 MOD 的 DLL 和 `MBSubModuleBase` 入口类。
- 源码仓库继续忽略 `bin/obj`；可分发 ZIP 由打包脚本生成，不将本地临时产物当作源码。
- 本机部署使用明确脚本，不让项目在普通编译时隐式覆盖游戏安装目录。

### 3. 141 个设计对象与 116 个运行时征兵点分层

已持久化地图中的 141 个帝国文化聚落对象包含：

```text
19 座城镇 + 97 个可征兵村庄 + 25 座城堡锚点 = 141
```

而 `GetBasicVolunteer` 实际需要查询的是有要人志愿兵槽的 19 座城镇和 97 个村庄，合计 116 个征兵点。冻结为：

- 建立一份包含 141 个对象的唯一机器可读设计源，保存地域、层级、坐标、城堡绑定与概率。
- 由脚本同源生成审阅地图与运行时 `regional_recruitment.xml`，不从最终 HTML 反向抓数据。
- 运行时 XML 仅列出 116 个可征兵聚落；25 座城堡用于构建期绑定校验，不伪装成可征兵点。
- 中央核心聚落也显式写入 `chance="0"`，以区分“设计为 0%”与“配置漏写”。
- 四个地域到根兵的映射在 XML 根部只定义一次，聚落行仅写 `region/tier/chance`，避免 116 次重复兵种 ID 造成地域与兵种不一致。

### 4. 模型注册、重入与聚落解析

只读骨架阶段必须实测：

1. 在哪个 `MBSubModuleBase` 回调中取得当前有效 `VolunteerModel` 并追加装饰器。
2. 记录内层模型的完整类型名，确认已保留原版、NavalDLC 与在本 MOD 之前生效的其他模型。
3. 防止重复包装；从主菜单返回后新建战役时，注册表和模型不沿用上一档的静态状态。
4. 若另一征兵 MOD 在本 MOD 之后再次替换 `VolunteerModel`，明确记录这是加载顺序兼容边界，不用 Harmony 强行抢回控制权。

聚落解析的第一版只使用 `notable.HomeSettlement`。若为空、未配置或解析失败，则原样返回内层模型结果并记录诊断；不在未验证前用 `CurrentSettlement` 将流亡、被俘或临时停留的要人错分到当前地点。

### 5. 随机源与可重复概率验收

- 真实战役志愿兵判定使用游戏随机源。
- `wx_pfc.sample` 使用独立固定种子，不读取、不消耗战役 RNG。
- 将随机判定抽成可测试的纯逻辑，便于对 0、0.30、0.55、0.80 和边界输入做自动化检查。
- 一万次模拟时，0% 必须严格为 0 次；30%/55%/80% 与目标值差异不超过 ±2 个百分点。
- 五点原型不仅覆盖核心与北、南、西、东四地域，还必须联合覆盖 0/30/55/80 四种概率；具体聚落 ID 在生成运行时配置时冻结。

### 6. 诊断输出与长期数据

- `sample`：输出种子、次数、命中数、实际比例和偏差。
- `audit_volunteers`：输出原版普通兵、地域兵、贵族兵及 T1–T4 聚合统计。
- `audit_parties`：只在 Day 0/30/60/120 等手动观察点执行，不进入持续战役更新。

长统计必须能导出为可比较的 CSV 或结构化日志；文件位置在只读 DLL 骨架阶段根据 Bannerlord 的可写目录实测后冻结，不默认向 `Program Files` 下的 MOD 目录写运行时文件。

### 实机验收修复（战役选项报错）

- 现象：战役选项滑块可调，但每项上方显示 `ERROR: Text with id str_campaign_options_description doesn't exist! Variation: str_wx_pfc_chance_frontier`（及 `str_campaign_options_type` 同类报错）。
- 证据：全库检索官方模块语言文件，`str_campaign_options_description` / `str_campaign_options_type` 两个基础 id **无任何模块定义**——该版本战役选项框架以"基础 id + 选项 id 变体"方式查找描述与类型标签，变体缺失时回退基础文本，基础缺失即报错（官方选项在此版本同样会报）。

- 补充根因（第二次复测仍报错后 IL 级定位）：`GameTextManager.LoadFromXML` 将 `<string>` 的 id **按 `.` 分割**——`id="基础.变体"` 即注册为变体条目；`TryGetText(id, variation)` 在变体缺失时**不回退基础文本**而直接失败。选项界面实际查找：名称 = `str_campaign_options_type.<选项id>`、描述 = `str_campaign_options_description.<选项id>`。因此仅提供基础 id 无效，必须提供带点组合 id。已为中/英各补 12 条组合条目（6 名称 + 6 描述），deploy 核验全部就位，提交 `3a1da89`。

这证明选项提供者、数值范围和界面控件本身已经被游戏发现，故障集中在文本注册层。

### 2. 根因纠正

此前把 `str_campaign_options_type.<variation>` 和 `str_campaign_options_description.<variation>` 直接写入 `ModuleData/Languages`，但这只是在语言翻译表中添加键，不能向游戏的 `GameText` 管理器创建新文本对象。

`NumericCampaignOptionData` 使用 `GameTexts.FindText(baseId, variation)`：

- `baseId` 为 `str_campaign_options_type` 或 `str_campaign_options_description`；
- `variation` 为 `str_wx_pfc_chance_frontier` 等选项 ID；
- 两者必须先由模块的 `GameText` XML 正式注册，语言文件再负责翻译其中引用的本地化键。

因此，记录 040 中“仅在语言文件补带点组合 ID 即可”的判断被本记录取代。

### 3. 实现

1. 新增 `ModuleData/wx_campaign_strings.xml`，注册 6 个标题与 6 个说明，共 12 个 GameText 变体。
2. 在 `SubModule.xml` 中新增 `<XmlName id="GameText" path="wx_campaign_strings" />`，仅供 `Campaign` 与 `CampaignStoryMode` 加载。
3. GameText 的 `text` 使用 `{=本地化键}英文后备文本`，延续原版 `module_strings.xml` 的写法。
4. 英文与简体中文语言文件保留 6 个标题翻译键和 6 个说明翻译键，删除此前无效的伪 GameText 组合条目。
